1 ภาพรวมและวัตถุประสงค์ของระบบ (Overview)

ระบบจองห้อง อาคาร C มหาวิทยาลัยราชภัฏนครปฐม ได้รับการออกแบบขึ้นเพื่อแก้ไขปัญหาความซ้ำซ้อนของการใช้ห้องเรียนและห้องประชุม รวมถึงลดขั้นตอนเอกสารแบบกระดาษ โดยนำระบบคอมพิวเตอร์มาช่วยบริหารจัดการทรัพยากรห้องเรียนในอาคาร C ชั้น 3 อย่างมีประสิทธิภาพสูงสุด

💡 จุดเด่นสำคัญของโครงงานนี้
  • ระบบตรวจสอบเวลาซ้อนทับอัตโนมัติ (Anti-Conflict Algorithm): ป้องกันการจองห้องซ้ำในช่วงเวลาเดียวกันแบบ Real-time ทั้งฝั่งหน้าบ้านและฐานข้อมูล
  • กระบวนการอนุมัติแบบ 2 ขั้นตอน (Two-Tier Approval Workflow): ตรวจสอบวัตถุประสงค์โดยฝ่ายวิชาการ ก่อนส่งมอบภารกิจเปิดห้องให้ฝ่ายอาคารสถานที่
  • การแยกโครงสร้างเชิงวัตถุอย่างชัดเจน (Clean OOP Architecture): แยกความรับผิดชอบของโค้ด (Single Responsibility) ในรูป Model/Service
  • ระบบแจ้งเตือนส่วนบุคคล (In-App Notification Hub): ผู้ใช้งานรับทราบสถานะการอนุมัติและแจ้งเตือนการเปิดห้องทันทีเมื่อเจ้าหน้าที่ดำเนินการ

3 วงจรชีวิตคำขอและการอนุมัติ 2 ระดับ (Two-Tier Approval Lifecycle)

จุดเด่นด้านการทำงานของระบบนี้ คือการจำลองขั้นตอนการปฏิบัติงานจริงของมหาวิทยาลัย ที่ต้องมีการตรวจทานความถูกต้องด้านการเรียนการสอนก่อน แล้วจึงส่งต่อให้ฝ่ายอาคารสถานที่จัดเตรียมแม่บ้านและช่างเปิดห้อง:

1

ส่งคำขอจองห้อง

นักศึกษาหรืออาจารย์เลือกห้อง ระบุหัวข้อการใช้งาน วันที่ และช่วงเวลา ระบบตรวจสอบการชนของเวลาอัตโนมัติ

status: pending
2

ฝ่ายวิชาการพิจารณา

เจ้าหน้าที่ฝ่ายวิชาการ (Academic Staff) ตรวจสอบวัตถุประสงค์ ความเหมาะสม และพิจารณา "อนุมัติ" หรือ "ปฏิเสธ"

status: approved / rejected
3

ฝ่ายอาคารเปิดห้อง

เจ้าหน้าที่ฝ่ายอาคาร (Building Staff) ได้รับการแจ้งเตือน นำกุญแจไปเปิดห้อง เปิดแอร์ และตรวจสอบความพร้อม

status: ready
4

เข้าใช้งานและเสร็จสิ้น

ผู้จองได้รับการแจ้งเตือนพร้อมสัญลักษณ์กุญแจ เข้าใช้ห้องตามเวลา เมื่อหมดเวลาสถานะจะเปลี่ยนเป็นเสร็จสิ้น

status: completed

4 โครงสร้างฐานข้อมูลอย่างละเอียด (Database Schema)

ระบบใช้ฐานข้อมูลชื่อ npru_room_booking ด้วยชุดอักขระ utf8mb4_unicode_ci รองรับภาษาไทยสมบูรณ์ ประกอบด้วย 4 ตารางหลัก:

ตารางที่ 1: rooms (ตารางข้อมูลห้องเรียน/ห้องประชุม)

ชื่อคอลัมน์ (Column) ชนิดข้อมูล (Type) Null ค่าเริ่มต้น (Default) คำอธิบายความหมายและการใช้งาน
id INT NO AUTO_INCREMENT รหัสประจำห้อง (Primary Key)
room_code VARCHAR(10) NO - รหัสห้อง เช่น C301, C302 (กำหนดเป็น UNIQUE ป้องกันรหัสซ้ำ)
room_name VARCHAR(100) NO - ชื่อห้อง เช่น "ห้องประชุมใหญ่", "ห้องเรียนปฏิบัติการ C305"
building VARCHAR(50) NO 'อาคาร C' ชื่ออาคารสถานที่ตั้งของห้อง
room_type VARCHAR(50) NO - ประเภทห้อง เช่น 'ห้องประชุม', 'ห้องเรียน' สำหรับใช้ตัวกรอง Filter
capacity INT NO 40 จำนวนที่นั่งสูงสุด (ระบบใช้ Validate จำนวนคนขอจองไม่ให้เกินความจุนี้)
floor VARCHAR(20) YES 'ชั้น 3' ชั้นที่ตั้งห้อง
facilities VARCHAR(255) YES 'โปรเจกเตอร์, ...' สิ่งอำนวยความสะดวก คั่นด้วยเครื่องหมายจุลภาค (,) เพื่อตัดเป็น Tag บน UI
status ENUM YES 'available' สถานะห้อง: 'available' (พร้อมใช้), 'maintenance' (ปิดปรับปรุง)

ตารางที่ 2: users (ตารางบัญชีผู้ใช้งานและเจ้าหน้าที่)

ชื่อคอลัมน์ (Column) ชนิดข้อมูล (Type) Null คำอธิบายความหมายและการใช้งาน
id INT NO รหัสผู้ใช้งาน (Primary Key)
student_id VARCHAR(20) YES รหัสนักศึกษา 9 หลัก (เช่น 674230036) กำหนดเป็น UNIQUE สำหรับนักศึกษา (Staff จะเป็น NULL)
name VARCHAR(100) NO ชื่อ - นามสกุลจริงของผู้ใช้งาน
email VARCHAR(150) NO อีเมลมหาวิทยาลัย (เช่น 674230036@webmail.npru.ac.th หรือ admin@npru.ac.th) UNIQUE
password VARCHAR(255) NO รหัสผ่านที่ผ่านการแฮชแบบความปลอดภัยสูงด้วย password_hash(..., PASSWORD_DEFAULT)
phone VARCHAR(20) YES เบอร์โทรศัพท์สำหรับติดต่อกรณีฉุกเฉินหรือประสานงานห้อง
role ENUM YES สิทธิ์ในระบบ:
  • student = นักศึกษาทั่วไป ยื่นจองและดูสถานะ
  • academic = เจ้าหน้าที่ฝ่ายวิชาการ อนุมัติเบื้องต้น
  • building = เจ้าหน้าที่ฝ่ายอาคาร ยืนยันเปิดห้อง
  • admin = ผู้ดูแลระบบสูงสุด ควบคุมได้ทุกฟังก์ชัน
created_at TIMESTAMP YES วันเวลาที่ลงทะเบียนสมัครสมาชิก

ตารางที่ 3: bookings (ตารางประวัติและการทำธุรกรรมจองห้อง)

ชื่อคอลัมน์ (Column) ชนิดข้อมูล (Type) FK Constraint คำอธิบายความหมายและการใช้งาน
id INT Primary Key เลขที่คำขอจอง (Booking Reference ID)
room_id INT FK → rooms(id) ON DELETE CASCADE รหัสห้องที่ต้องการจอง
user_id INT FK → users(id) ON DELETE SET NULL รหัสผู้ใช้งานที่ทำการส่งคำขอ (ถ้าไม่ได้ล็อกอินจะเป็น NULL)
requester_name VARCHAR(100) - ชื่อผู้ขอจอง (บันทึก Snapshot ไว้ แม้บัญชีผู้ใช้จะถูกแก้ไขในภายหลัง)
requester_email VARCHAR(150) - อีเมลผู้ขอจอง สำหรับใช้แมปข้อมูลและการแจ้งเตือน
requester_phone VARCHAR(20) - เบอร์โทรติดต่อผู้ขอจอง
topic VARCHAR(255) - หัวข้อหรือวัตถุประสงค์ในการใช้ห้อง เช่น "อบรมโครงงานไอทีปี 4"
booking_date DATE INDEX idx_booking_date วันที่ต้องการใช้ห้อง (รูปแบบ YYYY-MM-DD)
start_time TIME - เวลาเริ่มต้นใช้งานห้อง เช่น 09:00:00
end_time TIME - เวลาสิ้นสุดการใช้ห้อง เช่น 12:00:00
people INT - จำนวนผู้เข้าร่วมประชุมหรือผู้เรียนจริง
status ENUM INDEX idx_status สถานะของคำขอ: pending (รอวิชาการตรวจ), approved (วิชาการอนุมัติแล้ว), ready (อาคารเปิดห้องแล้ว), rejected (ปฏิเสธ), cancelled (ผู้ใช้ยกเลิกเอง)
academic_notes VARCHAR(255) - หมายเหตุหรือข้อความจากฝ่ายวิชาการ (เช่น "อนุมัติเพื่อการเรียนการสอนเสริม")
building_notes VARCHAR(255) - หมายเหตุจากฝ่ายอาคาร (เช่น "เปิดประตูห้องและแอร์ไว้ให้เรียบร้อยแล้ว")
created_at TIMESTAMP - วันเวลาที่ทำการส่งคำขอจองเข้าสู่ระบบ

ตารางที่ 4: notifications (ตารางแจ้งเตือนความคืบหน้าคำขอ)

ชื่อคอลัมน์ (Column) ชนิดข้อมูล (Type) คำอธิบายความหมายและการใช้งาน
id INT รหัสการแจ้งเตือน (Primary Key)
user_id INT รหัสผู้รับการแจ้งเตือน (FK → users.id ON DELETE CASCADE)
booking_id INT รหัสคำขอจองที่เกี่ยวข้อง (FK → bookings.id ON DELETE SET NULL)
title VARCHAR(150) หัวข้อแจ้งเตือน เช่น "🎉 คำขอจองห้อง C301 ได้รับการอนุมัติแล้ว"
message TEXT เนื้อหารายละเอียดของข้อความแจ้งเตือน
type ENUM หมวดหมู่การแจ้งเตือน: 'info', 'approved', 'ready', 'rejected', 'new_booking'
is_read TINYINT(1) สถานะการอ่าน: 0 = ยังไม่ได้อ่าน (Unread), 1 = อ่านแล้ว (Read)
created_at TIMESTAMP วันเวลาที่ข้อความถูกสร้างขึ้น

5 ความสัมพันธ์ระหว่างตาราง (Entity Relationships)

ความสัมพันธ์เชิงตรรกะ (Relational Constraints)
  • rooms (1) — (M) bookings: หนึ่งห้องสามารถมีการจองได้หลายช่วงเวลา เชื่อมโยงผ่าน bookings.room_id → rooms.id (เมื่อห้องถูกลบ รายการจองจะ CASCADE)
  • users (1) — (M) bookings: หนึ่งผู้ใช้งานสามารถส่งคำขอจองได้หลายครั้ง เชื่อมโยงผ่าน bookings.user_id → users.id (เมื่อผู้ใช้ถูกลบ จะ SET NULL เพื่อคงประวัติการใช้ห้องไว้)
  • users (1) — (M) notifications: หนึ่งผู้ใช้งานมีรายการแจ้งเตือนได้หลายรายการ เชื่อมโยงผ่าน notifications.user_id → users.id
  • bookings (1) — (M) notifications: แต่ละคำขอจองอาจสร้างการแจ้งเตือนหลายฉบับ (ยื่นคำขอ → วิชาการอนุมัติ → อาคารเปิดห้อง)

8 รายละเอียดคลาส Booking (Booking.php)

เป็นคลาสที่สำคัญที่สุดในการควบคุมกฎเกณฑ์ทางธุรกิจ (Business Rules) และการประมวลผลช่วงเวลา:

class Booking (Core Logic Engine)

classes/Booking.php
public function isConflict(int $roomId, string $date, string $start, string $end, ?int $excludeId = null): bool

อัลกอริทึมตรวจสอบเวลาชน (Interval Collision Algorithm):

ช่วงเวลาสองช่วงจะซ้อนทับกันก็ต่อเมื่อ เวลาเริ่มต้นของรายการใหม่ น้อยกว่าเวลาสิ้นสุดของรายการเดิม และเวลาสิ้นสุดของรายการใหม่ มากกว่าเวลาเริ่มต้นของรายการเดิม

SQL Conflict Logic SQL 
SELECT COUNT(*) FROM bookings
WHERE room_id = ?
  AND booking_date = ?
  AND status IN ('pending', 'approved', 'ready')
  AND (start_time < ? AND end_time > ?)

หากพบว่ามีรายการที่ตรงเงื่อนไข ฟังก์ชันจะคืนค่า true (เวลาชน ไม่สามารถจองได้)

public function create(int $roomId, ?int $userId, string $name, string $email, string $phone, string $topic, string $date, string $start, string $end, int $people): array

กฎการตรวจสอบก่อนบันทึก (Validation Pipeline):

  1. ตรวจความว่างเปล่าของฟิลด์จำเป็น (ชื่อ, อีเมล, วัตถุประสงค์)
  2. ตรวจรูปแบบอีเมลด้วย FILTER_VALIDATE_EMAIL
  3. ตรวจเวลา: เวลาเริ่มต้นต้องน้อยกว่าเวลาสิ้นสุดเสมอ (strtotime($start) < strtotime($end))
  4. ตรวจวันที่: ไม่อนุญาตให้เลือกวันย้อนหลังในอดีต
  5. ตรวจสถานะห้อง: หากห้องมีสถานะ 'maintenance' จะปฏิเสธการจองทันที
  6. ตรวจความจุ: จำนวนคน ($people) ต้องไม่เกินค่า capacity ของห้องนั้น
  7. เรียก isConflict() เพื่อยืนยันว่าไม่มีการจองซ้อนทับ
public function updateStatus(int $bookingId, string $status, ?string $notes = null, ?string $role = null): bool

อัปเดตสถานะของคำขอตามบทบาท โดยหากผู้กระทำเป็น 'academic' ข้อความบันทึกจะถูกเก็บลงฟิลด์ academic_notes หากเป็น 'building' จะถูกเก็บลงฟิลด์ building_notes

public function getRoomOccupancyToday(int $roomId): array

คำนวณการใช้งานห้องของวันนี้ในระดับ Real-time โดยเปรียบเทียบเวลาปัจจุบันของ Server (date('H:i:s')) กับช่วงเวลาที่ได้รับการอนุมัติ เพื่อระบุว่าห้องดังกล่าวกำลังมีคนใช้งานอยู่ ณ นาทีนี้หรือไม่ (is_occupied_now)
